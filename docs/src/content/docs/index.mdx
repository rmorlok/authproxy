## The problem it solves

Suppose you build a CRM and your customers want to connect their Salesforce,
Gmail, and Slack accounts. For each provider you need an OAuth client, a
callback endpoint, encrypted token storage, refresh logic, a way to show a
connection as broken when a token is revoked, and a settings page where users
can connect and disconnect. That code is nearly the same for every provider,
and it handles your customers' most sensitive credentials.

AuthProxy is that code, packaged as a service:

1. **You describe each provider once** in a YAML *connector*: its auth type,
   OAuth endpoints and scopes, and any setup questions.
2. **Your users connect their accounts** through AuthProxy's embeddable
   Marketplace UI. AuthProxy runs the OAuth or API-key flow and stores the
   result, encrypted, as a *connection*.
3. **Your backend calls the provider through AuthProxy.** It sends the request
   it wants to make along with a connection ID. AuthProxy adds the
   credentials, refreshes expired tokens, forwards the request, logs it, and
   returns the provider's response.

```mermaid
flowchart LR
    App["Your backend"] -->|"Provider request + connection ID"| AP["AuthProxy"]
    AP -->|"Same request + credentials"| API["Salesforce, Gmail, ..."]
    User["Your user"] -->|"Connect account"| MP["AuthProxy Marketplace"]
    MP --> AP
```

Your code still calls each provider's own API with its own URLs and payloads.
AuthProxy does not translate them into a common schema, and it does not run
workflows. Its job ends at authenticating and forwarding the request.
